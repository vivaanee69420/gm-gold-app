## Problem Statement

GM Dental (six practices, Kent / SE London / Sussex, ~25 clinicians, ~240 new consults/month, ~20,000 patient records in GoHighLevel) wants a zero-marketing-cost patient acquisition channel: existing patients refer friends, and when a referred friend completes paid treatment, the referrer earns a cash commission. The amount is a lever, not a constant: admin sets it in a dashboard (launch default £20 per completed referral). Commissions accumulate in an in-app wallet; past an admin-set threshold the referrer collects cash at any practice, and admin marks it paid.

A prototype of this concept exists (`gmdentalgoldcard/apps/gold-card`: Express + SQLite + PWA + Capacitor). The builder judged it not production-grade: no layered architecture, inline HTML views, shared admin API key, TypeScript where the team wants JavaScript. This project is a greenfield rebuild with proper standards, in a new folder, with the prototype kept as design reference only.

## Demand Evidence

- The Space Dental partnership call (Aug 2026) claimed one practice generated £663k/year from this referral channel with zero marketing spend (~34% of business revenue). This is second-hand vendor evidence, not GM Dental's own data. Honest status: the channel thesis is credible but unverified in-house.
- The business already committed engineering effort: a full prototype was built, and this referral app is system 1 of a six-system in-house platform plan.
- The strongest structural evidence: commission is released only on a completed, paid treatment. Every £20 paid out is attached to hundreds-to-thousands of pounds of verified treatment revenue, so the channel's worst case is cheap and its best case compounds.
- What would make demand evidence first-party: instrument the funnel from day one (invites sent → app activations → shares → referred sign-ups → consultations booked → treatments completed) and read it weekly.

## Status Quo

Referrals happen today by word of mouth: untracked, unrewarded, and invisible to the practices. GHL holds ~20k patient records with no referral attribution. The prototype is not deployed. Nobody at a front desk can answer "who sent us this patient, and what do we owe whom?" The cost of the status quo is every referral that never happened because the patient had no reason and no tool to make it.

## Target User & Narrowest Wedge

- **Referrer**: an existing GM Dental patient, verified at signup by matching their phone number against Dentally patient records. They carry the app; one tap shows their QR code and referral code; their wallet shows exactly how much they have earned and how far they are from collecting.
- **Referred friend**: installs the app, picks "I was referred", scans the referrer's QR with the in-app scanner or types the code, states treatment interest and consent. The practice team contacts them and books a consultation.
- **Practice admin / front desk**: the actual center of gravity. Sets the commission amount and payout threshold, confirms Dentally-detected completions with one click, and settles cash payouts at reception.

**Narrowest wedge** (the acceptance demo): admin sets reward to £20 → referrer shares from the app on WhatsApp → friend installs, enters the code, submits interest → front desk books and treats via normal workflow → Dentally sync proposes "this looks like referral #142, completed and paid" → admin confirms with one click → referrer's phone buzzes "£20 added to your wallet" and the threshold progress bar moves. Everything else is packaging around that loop.

## Constraints

- Stack is decided: Expo React Native (iOS + Android), Node.js + Express backend in modern JavaScript (ESM, not TypeScript, not Fastify), Supabase Postgres.
- Auth is decided: phone number + 6-digit OTP delivered via WhatsApp, SMS fallback. Sessions persist for months (WhatsApp/Instagram-style; no forced logouts).
- No web capture form at MVP. The referred friend uses the app. (Upheld twice against cross-model challenge; see Premises.)
- Cash payout is manual and in person at any practice; admin marks paid. No automated money movement at MVP.
- Must integrate with the existing stack: Dentally (treatment completion source of truth) and GoHighLevel (CRM; scope at MVP is an open question).
- UK compliance: GDPR consent capture on referred-friend contact, CQC/GDC advertising rules on incentive claims, tax treatment of cash rewards to be confirmed by the accountant.
- Six practices from day one; per-practice configuration must exist in the data model even if the launch uses one global rule.

## Premises

All confirmed by the builder during this session:

1. **Greenfield build** in a new folder (`gm-referral/`) beside `gmdentalgoldcard/`. The old app is design reference only. What carries over is design, not code: the status pipeline, the reward-rule shape, money as integer pennies, self-referral blocking, and the store-review lessons.
2. **Stack**: Expo RN + Express (ESM JavaScript) + Supabase Postgres, monorepo layout (`apps/mobile`, `apps/api`, `apps/admin`, `packages/shared`).
3. **Both roles use the app.** Referred friends install it and enter or scan the code in-app. No web form at MVP. This was challenged by two independent models on install-friction grounds and upheld by the builder both times. Mitigation: instrument share-link taps vs completed referred sign-ups from day one; a hosted web capture page is the documented Phase 2 lever if completion falls below ~30%.
4. **Referrer eligibility**: referrers must be existing patients, verified by phone-number match against Dentally records at onboarding. Unmatched numbers go to an admin review queue rather than being silently rejected.
5. **Auth**: WhatsApp OTP (SMS fallback), Supabase Auth sessions with long-lived refresh tokens.
6. **Commission trigger**: earned only when the referred patient's treatment is completed and paid. Dentally detects and **proposes**; a human confirms with one click. Never fully unattended auto-credit of cash. (This restores the builder's own words: "make it manual".)
7. **Payout**: cash wallet. Default £20 per completed referral, amount dynamic (admin-set), payout threshold admin-set (working default £100), collection in person at any practice, admin marks paid. Wallet is an append-only ledger; balances are derived, never stored as a mutable number.

## Cross-Model Perspective

An independent Claude subagent with no view of this conversation reviewed the premises cold. Its findings, close paraphrase:

- **Steelman**: this is not "an app that pays £20 for referrals"; it is a zero-media-cost acquisition channel with deterministic CAC, and the identity + messaging + Dentally rails it lays down are the down payment on the other five systems of the platform.
- **Sharpest insight**: from the builder's own words ("the amount should be set by the admin in the admin dashboard"), the admin dashboard is the actual product; the patient app is its distribution skin. The system lives or dies at six front desks.
- **Refinement adopted**: Dentally should propose completions, not auto-commit them. Phone-format mismatches, family members sharing a number, partial payments, NHS courses, and refunds make unattended cash crediting misfire. A confirm click costs two seconds and preserves front-desk trust.
- **Challenged premise**: it argued the referred friend should get a web form, not an app install (typical 70%+ drop-off on app-install steps). The builder overrode this explicitly, twice. The override is recorded, and the funnel metric that would falsify or vindicate it is a Success Criterion below.
- Its 48-hour prototype sketch became the basis of the acceptance demo in the wedge above.

## Approaches Considered

### Approach A: Supabase-managed everything (minimal viable)
Supabase Auth does phone OTP via Twilio Verify's WhatsApp channel; Express carries only business logic; notifications also sent via Twilio. Effort M, Risk Low. Pros: zero hand-rolled auth, fastest working login, one vendor. Cons: Twilio markup on every OTP and message forever; WhatsApp templates managed through Twilio's layer; auth lives in vendor config, not the codebase.

### Approach B: Own the whole channel (maximum control)
Custom OTP issuance and JWT/refresh sessions built in Express; WhatsApp Cloud API (Meta direct) for OTPs and notifications; Supabase used as managed Postgres only. Effort L, Risk Med. Pros: everything in plain JavaScript in the repo, no per-message middleman, cheapest at scale. Cons: hand-rolled refresh rotation, theft detection, and rate limiting are where solo-built apps grow security holes; Meta business verification sits on the critical path before login works at all.

### Approach C: Supabase sessions + Meta delivery (hybrid) — CHOSEN
Supabase Auth issues and verifies OTPs and manages long-lived sessions, but its send-SMS hook points at the Express API, which delivers the code via WhatsApp Cloud API (with SMS fallback). Status notifications ride the same Meta integration. Effort M, Risk Low-Med.

## Recommended Approach

**Approach C.** Rationale: the persist-for-months session requirement comes free from battle-tested auth machinery (zero custom auth code to get wrong), while the WhatsApp channel stays fully owned for both OTP delivery and the retention notifications that keep months-long "pending" referrals emotionally alive. One Meta integration, two jobs, no Twilio markup (Meta's own per-conversation fees still apply — see open question 10). The known risk (Meta business verification lead time) is mitigated by starting verification on day one and shipping SMS fallback regardless, because the fallback is also the delivery path for numbers without WhatsApp.

Architecture at a glance (full detail in FLOWS.md and REQUIREMENTS.md):

```
apps/mobile   Expo React Native. Roles: referrer, referred. WhatsApp OTP login,
              QR display + scanner, wallet, referral statuses, share sheet.
apps/api      Node 22+, Express, ESM JavaScript. Layered: routes → controllers →
              services → repositories. Owns: OTP delivery hook, wallet ledger,
              referral pipeline, Dentally sync worker (propose), WhatsApp/SMS
              notification service, admin endpoints, GHL push (if MVP).
apps/admin    React (Vite) web dashboard. Levers (amount, threshold), confirm-
              completions queue, payout queue, pipeline board, liability report.
Supabase      Postgres (RLS on), Auth (phone OTP via send-SMS hook).
Meta WhatsApp Cloud API: auth template (OTP) + utility templates (status, wallet).
Dentally      REST API. Patient phone match at onboarding; completed+paid
              treatment detection feeding the propose queue.
```

The approved wireframe (`wireframe-sketch.png`) fixes screen hierarchy: QR first on the referrer home, wallet with threshold progress second, statuses third; scan-or-type plus consent on one referred screen; admin leads with the two levers beside the confirm and payout queues.

## Success Criteria

- The acceptance demo (wedge above) runs end to end on real devices with a Dentally-proposed completion, before any store submission. If Dentally provides no sandbox, a staged test treatment record (or a manually injected sync event flagged test-only) satisfies the gate — the demo must not be hostage to a real referred patient completing real treatment (outside voice, 2026-08-14).
- Apps live in both stores; invited patients can activate with WhatsApp OTP in under 60 seconds; OTP delivery success ≥99% with fallback.
- Admin can change commission amount and payout threshold with zero deploys, and the change is visible in the app immediately.
- Funnel instrumented from day one: invites → activations → shares → referred sign-ups → booked consults → completions. Premise-3 tripwire (re-anchored by eng review): `code_entered → referral_submitted` completion plus store-install attribution; if completion collapses, the web-form fallback decision is triggered. `share_tapped` is reported but treated as noisy.
- Every wallet movement is an append-only ledger row with an audit trail; balances always equal the sum of the ledger.
- First 90 days (channel health, not app health): ≥10 completed referred treatments across the group, with commission liability and payout latency visible on the admin dashboard.
